지난 2월에 [AI와 함께하는 문서 주도 개발](/ko/2026/2/27/doc-driven-development-with-ai)이라는 글을 썼습니다. 여러 에이전트와 세션을 오가면서 매번 맥락을 다시 설명하는 비용을 줄이려고, 요구사항과 설계, 구현 계획을 Markdown 문서에 남겨두고 이어서 작업하는 방식이었습니다.

그 뒤로도 업무와 개인 프로젝트에서 계속 이 방식을 사용했습니다. 기본 생각은 지금도 같습니다. **대화가 끝나더라도 프로젝트의 맥락은 문서에 남아 있어야 한다**는 것입니다.

다만 계속 써보니, 문서를 처음 잘 만드는 것만으로는 충분하지 않았습니다. 구현이 진행되면 문서도 바뀌어야 하고, 기능이 늘어나면 문서가 여러 곳으로 나뉘고, 예전 계획이 현재 기준처럼 남아 있기도 합니다. 이제는 다음 세션에 무엇을 읽히느냐만큼, **그 문서들이 계속 믿고 참고할 수 있는 상태인가**가 중요해졌습니다.

이 과정에서 다듬은 방법론과 에이전트 역할, 그리고 사람이 문서 전체를 살펴보기 위한 뷰어를 [DocAtlas](https://github.com/superlucky84/docatlas)라는 리포에 모았습니다. 이번 글은 이전에 공유했던 개인적인 작업 방식이 어떻게 이 리포로 이어졌는지에 대한 이야기입니다.

<h2 id="document-management" class="py-1 border-b dark:border-[#313131]">
  {'스펙보다 문서 관리에 무게를 둔 이유'}
</h2>

요구사항과 설계를 먼저 정리하고 구현한다는 점에서, 제가 하는 일은 기존의 스펙 기반 개발이나 문서 기반 개발과 크게 다르지 않습니다. 결정의 근거와 인계 내용을 남기는 것도 오래된 습관입니다. 이런 습관들을 제가 AI 에이전트와 일하는 방식에 맞춰 정리하고, 반복해서 쓸 수 있도록 만든 것입니다.

그럼에도 굳이 **문서 주도 개발**이라고 부르는 이유는, 제가 관심을 두는 중심이 스펙 자체보다 **문서와 그 문서를 관리하는 일**에 있기 때문입니다.

무엇을 만들지 정확히 적는 것은 당연히 중요합니다. 거기에 더해 왜 그렇게 결정했는지, 어디까지 구현했는지, 무엇으로 검증했는지, 아직 결정하지 않은 것은 무엇인지도 함께 남기고 싶습니다. 기능을 배포한 뒤에도 이 문서들이 프로젝트의 기억으로 남았으면 합니다.

제가 계속 확인하고 싶은 질문은 이쪽입니다.

> 지금 이 문서들을 읽으면, 다른 에이전트가 프로젝트를 이어서 작업할 수 있을까?

스펙 기반 개발에서도 충분히 다룰 수 있는 내용입니다. 문서 주도라는 이름은 제가 어디에 무게를 두는지 설명하는 표현이라고 생각합니다. 이 관점은 리포의 [방법론 문서](https://github.com/superlucky84/docatlas/blob/main/METHOD.ko.md)에도 정리했습니다.

<h2 id="documents-in-context" class="py-1 border-b dark:border-[#313131]">
  {'네 가지 문서에서 시작하되, 프로젝트에 맞게 쓰기'}
</h2>

지금 회사에서도 레거시와 새 코드가 공존하고, 디렉터리 트리도 꽤 어수선해진 프로젝트에 이 방식을 적용해보고 있습니다. 새 프로젝트에서 문서 몇 개로 시작할 때와는 고민이 달랐습니다. 이미 복잡한 구조 안에 문서까지 더해지는데, 이것들을 어디에 두면 좋을지가 먼저 걸렸습니다.

모노레포이거나 스캐폴딩 구조가 복잡한 경우, 혹은 기능이 아주 많은 프로젝트라면 더 그렇습니다. 모든 기능의 요구사항과 설계, 구현 계획을 한곳에 모아놓는 모습을 떠올리니, 나중에는 그 자체가 **문서 폭탄**처럼 느껴질 것 같았습니다. 맥락을 쉽게 찾으려고 쓰는 문서인데, 문서 더미에서 필요한 것을 찾는 일이 또 하나의 부담이 될까 봐 꺼려졌습니다.

여기서 힌트를 얻은 것이 테스트 파일을 두는 방식이었습니다. 프로젝트에 따라 다르지만, 테스트를 대상 모듈 바로 옆에 작성하는 경우가 많습니다. 해당 코드를 볼 때 테스트도 함께 찾을 수 있고, 무엇을 검증하는 테스트인지 위치만으로도 짐작할 수 있습니다. 문서도 자기가 설명하는 코드 가까이에 있으면 비슷하게 따라갈 수 있겠다는 생각이 들었습니다.

다만 문서를 어느 정도 크기로 묶을지는 따로 생각해야 했습니다. 보통 코드는 목적이나 기능, 성격에 따라 관련 함수와 모듈을 모아둡니다. 함께 이해하고 수정해야 할 것들을 가까이 두는 것은 코드의 응집력을 높이고, 모듈화와 추상화의 경계를 잡는 일이기도 합니다. 문서의 위치도 이렇게 코드에 이미 드러나 있는 묶음을 따라가면 좋겠다고 생각했습니다.

그래서 개별 모듈마다 `docs/`를 만들기보다는, **관련 모듈들이 모인 적절한 위치에 문서 섹션을 두는 방식**을 택했습니다. 예를 들어 주문이나 결제라는 기능을 이해하는 데 여러 모듈이 함께 필요하다면, 그 묶음을 설명하는 문서를 둘 자리를 잡는 것입니다.

이 경계를 잡는 일은 사람이 에이전트를 도와줘야 할 부분이라고 생각합니다. 프로젝트를 아는 사람이 어떤 코드들이 하나의 기능을 이루는지, 어디까지 같은 맥락으로 읽어야 하는지 짚어주고, 에이전트와 함께 문서 위치를 정하는 것입니다. 특히 레거시가 섞인 프로젝트에서는 디렉터리 이름만으로 드러나지 않는 관계도 있으니까요.

### 기본 문서와 관리 규칙

문서를 두는 위치는 유연하게 정하되, 이전 글에서 소개한 네 가지 문서의 역할은 유지합니다.

| 문서                       | 남겨둘 내용                                |
| -------------------------- | ------------------------------------------ |
| `REQUIREMENTS.md`          | 무엇을 만들지, 범위와 제약은 무엇인지      |
| `DESIGN.md`                | 어떻게 만들지, 무엇을 왜 결정했는지        |
| `IMPLEMENT.md`             | 어떤 단계로 진행하며, 지금 어디까지 왔는지 |
| `MANUAL_TEST_CHECKLIST.md` | 사람이 어떤 동작을 확인해야 하는지         |

여러 그룹에서 함께 쓰는 계약이 되면 공통 상위로 옮기고 링크를 남깁니다. 별도 명세가 필요하면 `CONTRACTS.md` 같은 문서로 나누되, 같은 내용을 여러 기준본으로 복제하지 않습니다.

예를 들어 checkout과 catalog가 각각 관련 모듈들을 묶은 기능 영역이라면, 이런 구조가 될 수 있습니다.

```text
repo/
  docs/payments/CONTRACTS.md
  services/checkout/docs/
    REQUIREMENTS.md
    DESIGN.md
    IMPLEMENT.md
    MANUAL_TEST_CHECKLIST.md
  web/catalog/docs/
    REQUIREMENTS.md
    DESIGN.md
```

모든 수정에 네 가지 문서를 만들 필요도 없습니다. 작은 수정은 문서 없이 진행할 수 있고, 이미 문서가 있는 기능이라면 그 기준을 먼저 읽고 필요한 부분을 갱신하면 됩니다. 기존 프로젝트에 이 방법을 도입한다고 문서 전체를 한 번에 같은 형식으로 바꿀 필요는 없습니다.

대신 남겨두기로 한 문서에는 기준을 둡니다. 미결정 사항은 `TBD`로 표시하고, 결정에는 근거를 붙이고, 진행 상태에는 테스트 결과를 남깁니다. 현재 인계 내용은 `IMPLEMENT.md` 안의 한 블록으로 유지합니다. 완료한 일, 다음 작업, 막힌 점, 최신 커밋을 적고, 이전 상태는 Git 이력으로 확인합니다.

저에게 **문서를 코드처럼 관리한다**는 것은 이런 의미입니다. 현재 참고할 기준본을 명확히 하고, 동작이나 계약이 바뀌면 같은 변경에서 문서도 고치고, 예전 상태는 버전 관리에 맡기는 것입니다. 문서를 계속 추가하는 것뿐 아니라 합치고 옮기고 정리하는 일도 개발의 일부로 보는 셈입니다.

이 유지와 정리도 에이전트에게 맡깁니다. 그래서 초안을 만드는 절차뿐 아니라, 구현하면서 문서를 갱신하고 그 내용이 실제 변경과 맞는지 확인하는 역할까지 필요해졌습니다.

<h2 id="agent-roles" class="py-1 border-b dark:border-[#313131]">
  {'설계자, 구현자, 리뷰어의 역할 나누기'}
</h2>

이전 글에서는 요구사항을 듣고 문서로 정리하는 설계자의 역할을 주로 소개했습니다. DocAtlas에는 구현자와 리뷰어까지 포함해 세 가지 역할의 스킬과 룰을 모았습니다.

| 역할        | 맡기는 일                                                                 |
| ----------- | ------------------------------------------------------------------------- |
| Designer    | 대화를 요구사항과 설계, 단계별 계획, 검증 문서로 정리하기                 |
| Implementer | 문서를 읽고 한 단계씩 구현하며 테스트 근거와 문서, 인계를 갱신하기        |
| Reviewer    | 변경 사항을 문서와 프로젝트 규칙, 요청 의도에 비춰 읽기 전용으로 검토하기 |

핵심은 구현자에게 코드를 만드는 일과 함께 **문서를 현재 상태로 맞추는 책임**을 주는 것입니다. 한 단계가 끝났을 때 무엇을 구현했고 무엇을 검증했는지, 다음에 무엇을 해야 하는지가 남아야 다음 세션에서 같은 설명을 반복하지 않을 수 있습니다.

리뷰어는 파일을 직접 고치지 않고 문제와 심각도를 보고합니다. 구현한 결과를 다시 문서의 의도와 비교하는 절차를 별도 역할로 정리해두고 싶었습니다.

이 역할들은 에이전트가 따를 Markdown 스킬과 룰로 정리했으며, 구체적인 구성은 [agent-kit](https://github.com/superlucky84/docatlas/tree/main/agent-kit)에서 볼 수 있습니다.

<h2 id="keeping-the-bigger-picture" class="py-1 border-b dark:border-[#313131]">
  {'문서의 흐름을 주도하며 전체 그림을 놓치지 않기'}
</h2>

에이전트의 역할을 나누는 것과 함께, 사람이 어떤 판단을 계속 맡을지도 중요합니다. 문서의 위치와 흐름을 사람이 함께 결정하는 과정은, 저에게도 프로젝트를 다시 이해하는 시간이 됩니다. 어떤 기능이 어떤 모듈로 이루어져 있고, 무엇을 공유하며, 경계는 어디인지 생각하게 됩니다.

에이전트에게 작업을 맡기고 결과만 확인하다 보면, 기능은 계속 늘어나는데 정작 사람은 프로젝트가 어떻게 흘러가고 있는지 놓치기 쉽다고 생각합니다. 개별 작업의 완료 여부는 알아도, 왜 이런 구조가 되었고 이번 변경이 다른 영역에 어떤 영향을 주는지는 점점 설명하기 어려워질 수 있습니다. 그래서 **문서를 어떤 단위로 묶고, 무엇을 기준으로 삼고, 어떻게 이어갈지는 사람이 주도하는 것**이 중요하다고 봅니다. 이 판단에 계속 참여하는 것이 모든 것을 에이전트에게 넘긴 채 프로젝트에 대한 이해까지 잃어버리는 상황을 피하는 데 도움이 됩니다.

세부 구현과 문서 갱신을 에이전트에게 맡길수록, 사람은 그 여유를 **아키텍트의 관점에서 프로젝트 전체를 바라보는 데** 쓸 수 있었으면 합니다. 기능 사이의 관계, 책임의 경계, 공통으로 유지해야 할 계약, 앞으로 변경이 쌓일 방향을 살피는 것입니다. 문서의 흐름을 사람이 이끌어가는 일은 이런 시야를 유지하는 방법이기도 합니다. 에이전트의 작업 속도를 따라가는 동안에도 전체 흐름을 놓치지 않고, 더 큰 범위에서 구조의 건강함을 판단할 수 있는 관점을 갖고 싶습니다.

<h2 id="document-map" class="py-1 border-b dark:border-[#313131]">
  {'사람이 보기 위한 문서 지도가 필요했습니다'}
</h2>

사람이 이런 역할을 하려면, 프로젝트의 문서가 어디에 있고 어떻게 연결되는지 살펴볼 수 있어야 합니다. 문서를 코드 가까이에 두면 해당 기능을 수정할 때 찾기는 편합니다. 하지만 기능이 늘수록 프로젝트 전체의 문서가 어디에 있는지 한눈에 파악하기는 어려워집니다.

AI가 파일을 찾고 읽을 수 있어도, 사람인 저는 전체 구조를 알고 싶었습니다. 어떤 기능에 문서가 있고, 예전 계획은 어디에 남아 있고, 비슷한 내용을 적은 문서가 여러 곳에 흩어져 있지는 않은지 살펴볼 수 있어야 했습니다.

특히 기존 프로젝트에는 레거시가 있습니다. 문서에 적힌 내용만으로는 그 기능이 지금도 쓰이는지, 예전 전제에서 작성된 것인지 판단하기 어려울 수 있습니다. 사람은 이런 배경을 알고 에이전트에게 힌트를 줄 수 있습니다.

예를 들어, 뷰어로 전체를 살펴본 뒤 이런 식으로 요청하고 싶은 것입니다.

> 이 두 문서는 같은 기능의 예전 계획과 새 계획 같아. 실제 구현과 비교해서 기준본을 정리해줘.

> 이 계약은 결제 기능만 쓰는 게 아니라 주문에서도 쓰고 있어. 공유 문서로 옮기고 참조를 맞춰줘.

> 이 기능은 이제 사용하지 않아. 관련 코드와 문서를 확인해서 정리할 범위를 알려줘.

이런 판단에 필요한 전체 그림을 보기 위해 만든 것이 DocAtlas의 문서 뷰어입니다.

위 화면은 리포에 포함된 가상의 쇼핑몰 예제입니다. 왼쪽에서 기능과 문서의 계층을 살펴보고, 오른쪽에서 선택한 Markdown 문서를 읽을 수 있습니다. 이미지를 누르면 크게 볼 수 있습니다.

문서 본문과 경로를 검색하고, 검색 결과가 어느 위치에 있는지 지도로 돌아가 확인할 수 있습니다. 파일을 수정하면 변경도 반영됩니다. 기존 문서를 볼 때 네 가지 문서가 모두 갖춰져 있을 필요는 없고, 추가 문서 폴더나 프로젝트 전체의 Markdown을 수집하도록 범위를 조정할 수도 있습니다. 자세한 동작은 [문서 지도 가이드](https://github.com/superlucky84/docatlas/blob/main/guide/document-map.md)와 [설정 가이드](https://github.com/superlucky84/docatlas/blob/main/guide/configuration.md)에 정리했습니다.

뷰어 자체가 문서를 고치거나 무엇이 레거시인지 판정하지는 않습니다. 사람이 문서의 분포와 내용을 파악하고, 에이전트에게 어떤 확인과 정리를 맡길지 판단하는 데 쓰는 화면입니다.

모든 문장을 사람이 직접 읽고 관리하려는 것은 아닙니다. 대략적인 기능과 문서의 위치, 오래된 맥락을 파악해서 **에이전트가 살펴봐야 할 방향을 짚어줄 수 있는 정도**를 원했습니다.

<h2 id="getting-started" class="py-1 border-b dark:border-[#313131]">
  {'직접 써보려면'}
</h2>

뷰어는 Node.js 22 이상과 npm이 있는 환경에서, 살펴볼 프로젝트의 루트로 이동해 실행하면 됩니다.

```sh
cd /path/to/project
npx docatlas
```

터미널에서 로컬 서버가 실행되고 브라우저로 문서 지도가 열립니다. 대상 프로젝트를 빌드하거나 그 프로젝트에 의존성을 추가할 필요는 없습니다. JavaScript 프로젝트가 아니어도 Markdown 문서가 있는 프로젝트에 사용할 수 있습니다.

기본적으로 프로젝트 안의 `docs/` 아래 Markdown과 네 가지 기본 이름의 문서를 찾습니다. 다른 위치에 있는 문서까지 살펴보고 싶으면 다음처럼 실행할 수 있습니다. 제외 경로와 `.gitignore` 규칙은 계속 적용됩니다.

```sh
npx docatlas --docs-dir documentation
npx docatlas --all-md
```

에이전트 역할도 함께 써보고 싶다면 설치할 파일을 먼저 확인한 뒤 설치하면 됩니다.

```sh
npx docatlas agents install --dry-run
npx docatlas agents install
```

설치한 뒤에는 에이전트에게 `doc-driven-designer-v1`으로 요구사항을 정리하거나, `doc-driven-implementer-v1`으로 특정 단계를 구현하거나, `doc-driven-reviewer-v1`으로 변경 사항을 리뷰해달라고 요청할 수 있습니다. 설치 옵션은 [에이전트 킷 안내](https://github.com/superlucky84/docatlas/blob/main/agent-kit/README.md)에 있습니다.

방법론만 참고해도 되고 뷰어만 사용해도 됩니다. 리포에는 [문서 세트를 갖춘 예제](https://github.com/superlucky84/docatlas/tree/main/examples/sample-shop)와 DocAtlas 자체를 개발하며 작성한 [기획 문서](https://github.com/superlucky84/docatlas/tree/main/docs)도 있으니, 실제로 어떤 내용을 남기는지 궁금하다면 같이 살펴볼 수 있습니다.

<h2 id="still-evolving" class="py-1 border-b dark:border-[#313131]">
  {'계속 써보면서 바꾸는 중입니다'}
</h2>

처음에는 에이전트를 바꿀 때 설명을 덜 반복하고 싶어서 시작했습니다. 계속 사용하다 보니, 문서를 남기는 것에서 그 문서들을 오래 관리하는 쪽으로 관심이 넓어졌습니다. 그래서 역할을 더 나누고, 작성과 정리 규칙을 다듬고, 사람이 전체를 볼 수 있는 도구도 만들게 됐습니다.

사람이 문서를 전부 작성하고 관리해야 했다면 유지하기 힘들었을 것 같습니다. 지금은 AI가 주로 참고할 문서를 AI에게 쓰고 관리하게 할 수 있습니다. 그렇게 줄어든 부담만큼 저는 프로젝트의 구조와 방향을 살피고, 필요한 결정을 내리고, 레거시에 대한 힌트를 주는 데 더 집중하고 싶습니다.

[DocAtlas](https://github.com/superlucky84/docatlas)는 그렇게 쓰기 위해 만든 현재의 결과물입니다. 이전 글에서 소개한 방식이 실제 작업을 거치며 어떻게 달라졌는지 궁금했던 분들께도 참고가 되었으면 합니다.
